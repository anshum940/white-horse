# White Horse Accounting Logic and Validation Catalogue

## 1. Regulatory configuration

The initial seeded taxonomy follows the broad presentation structure of Schedule III Division I and incorporates the 2021 amendment categories. It does not assert that automated classification replaces the preparer's assessment. Each company stores its selected framework, taxonomy version, materiality, rounding, and policy choices.

Applicable guidance must be revalidated for the reporting date. The application exposes taxonomy/rule version references on every final report.

## 2. Monetary and sign convention

- Store money as integer paise.
- `signedAmount = debitPaise - creditPaise`.
- Debit balances are positive; credit balances are negative.
- Presentation amounts are generated by applying the taxonomy node's normal balance:
  - Debit-normal display = `signedAmount`.
  - Credit-normal display = `-signedAmount`.
- A negative displayed amount is never silently reclassified. It remains visible and raises a validation unless an approved mapping/presentation rule permits it.
- Round only at report presentation. Calculations and reconciliations use paise.

## 3. Trial Balance calculations

For each row:

```text
openingSigned = openingDebit - openingCredit
movementSigned = movementDebit - movementCredit
calculatedClosingSigned = openingSigned + movementSigned
reportedClosingSigned = reportedClosingDebit - reportedClosingCredit
rowClosingDifference = calculatedClosingSigned - reportedClosingSigned
```

For the full import:

```text
sum(openingDebit) == sum(openingCredit)
sum(movementDebit) == sum(movementCredit)
sum(reportedClosingDebit) == sum(reportedClosingCredit)
sum(calculatedClosingSigned) == 0
```

Files containing only closing debit/credit are supported; movement validation becomes not applicable and is disclosed.

## 4. Mapping rules

Every material active ledger maps to exactly one leaf presentation node for its primary statement. It may additionally reference a note node, cash-flow class, ratio tags, and disclosure attributes.

Mapping order:

1. Exact approved company mapping by ledger code.
2. Prior-period approved mapping for the same ledger identity.
3. User-defined mapping template match.
4. Deterministic keyword/group suggestion with confidence and explanation.
5. Unmapped—requires preparer action.

Suggestions are never posted automatically. Changes after approval create a new mapping version and require review. Current/non-current classification follows the configured reporting framework and user-provided operating-cycle/maturity evidence; the engine only flags inconsistencies.

## 5. Adjusted Trial Balance

Only `POSTED` adjustments affect statements:

```text
adjustmentSignedByLedger = sum(posted debit lines) - sum(posted credit lines)
adjustedClosingSigned = activeImport.calculatedClosingSigned + adjustmentSignedByLedger
```

Regrouping adjustments may use taxonomy nodes without changing ledger master classification, but still require balanced debit/credit lines and approval.

## 6. Statement logic

### 6.1 Balance Sheet

Aggregate adjusted signed balances by mapped Balance Sheet node, then roll leaf values to parents. Assets use debit-normal presentation; equity and liabilities use credit-normal presentation.

Presentation order is Equity and Liabilities first, followed by Assets. This order is applied after all sections, totals and the current-profit bridge are calculated, so it does not change the accounting equation, mapped amounts or drill-down lineage.

Current-period profit/loss from the Statement of Profit and Loss is bridged to equity for presentation where the TB has not already closed nominal accounts. The bridge is a calculated statement line, not a ledger mutation, and is explicitly included in reconciliation.

```text
assets = nonCurrentAssets + currentAssets
equityAndLiabilities = equity + nonCurrentLiabilities + currentLiabilities
balanceSheetDifference = assets - equityAndLiabilities
```

Finalisation requires a zero-paise balance-sheet difference.

### 6.2 Statement of Profit and Loss

Revenue/income nodes use credit-normal presentation; expense/tax nodes use debit-normal presentation.

```text
totalIncome = revenueFromOperations + otherIncome
EBITDA = totalIncome - operatingExpensesExcludingDepreciationFinanceTax
EBIT = EBITDA - depreciationAndAmortisation
profitBeforeTax = EBIT - financeCosts + configuredNonOperatingItems
profitAfterTax = profitBeforeTax - currentTax - deferredTax
```

Exceptional and prior-period items are separately presented when configured and material. The exact placement is taxonomy-driven.

### 6.3 Cash Flow Statement (indirect method)

```text
cashFromOperations =
  profitBeforeTax
  + nonCashExpenses
  - nonCashIncome
  +/- workingCapitalChanges
  - incomeTaxesPaid

netCashMovement = operating + investing + financing + exchangeEffect
closingCash = openingCash + netCashMovement
cashFlowDifference = statementClosingCash - adjustedTBCashAndCashEquivalents
```

Each mapped ledger or adjustment carries a cash-flow class and optional non-cash flag. Unclassified material movements block finalisation. A cash-flow reconciliation difference of any paise blocks finalisation.

### 6.4 Statement of Changes in Equity

For configured frameworks/entities:

```text
closingEquityComponent = opening + restatements + ownerTransactions + currentProfit + OCI/transfers
```

Each movement must reconcile to mapped equity ledgers and approved adjustments.

### 6.5 Notes and cross-references

Face statement nodes marked `noteRequired` must reference a note. Note totals must equal the corresponding face amount before presentation rounding. Differences caused solely by displayed rounding are disclosed through a rounding adjustment line when configured; raw paise totals must still reconcile.

The automatic disclosure layer has a strict evidence boundary:

- company identity, CIN, registered office, industry and reporting dates come from the selected company/period master;
- numerical note text comes from mapped ledger balances, comparative balances and posted adjustments;
- a zero or absent mapped balance is labelled `NO_BALANCE`, not automatically `NOT_APPLICABLE`;
- ratios and regulatory disclosures that need operating explanations, statutory registers, legal confirmations, ageing detail or other non-ledger evidence are labelled `REQUIRES_WORKPAPER`; and
- generated text remains a draft until the preparer and reviewer complete the note checklist.

## 7. Rounding

- Supported display scales: rupees, thousands, lakhs, crores.
- Raw calculations remain in paise.
- Default rounding is half-away-from-zero at the chosen scale.
- A report-level rounding allocator may distribute display-only differences to designated lines, never to raw balances.
- Report headers state the currency and scale.

## 8. Ratio definitions

All formulas show their exact configured components and drill-down.

| Ratio | Default formula |
| --- | --- |
| Current ratio | Current assets / Current liabilities |
| Debt-equity | Total debt / Shareholders' equity |
| Debt service coverage | Earnings available for debt service / Interest and principal debt service |
| Return on equity | Profit after tax / Average shareholders' equity |
| Inventory turnover | Cost of goods sold / Average inventory |
| Trade receivables turnover | Revenue from operations / Average trade receivables |
| Trade payables turnover | Purchases or relevant operating cost / Average trade payables |
| Net capital turnover | Revenue from operations / Average working capital |
| Net profit ratio | Profit after tax / Revenue from operations |
| Return on capital employed | EBIT / Average capital employed |
| Return on investment | Investment income / Average invested funds |
| Interest coverage | EBIT / Finance costs |

If a denominator is zero or unavailable, the ratio is `N/A`, not zero. The report states whether average or closing balances were used and flags missing comparative inputs.

## 9. Validation execution

Rules run at import, mapping, adjustment submission, review, and finalisation. A complete run records the ruleset and dataset hashes. Severity meanings:

- `BLOCKING`: cannot proceed/finalise; no override.
- `ERROR`: materially inconsistent; may be overridden only by reviewer with reason if the rule permits.
- `WARNING`: requires documented review.
- `INFO`: observation or improvement.

RAG status: Red if any blocking/error is open; Amber if warnings are open; Green only when no blocking/error and all warnings are resolved or approved.

## 10. Validation catalogue

The following rules are executed by the current deterministic workspace validator. Import-preview controls (file type, size, row syntax, semantic column selection and exact activation totals) run separately before a TB is activated.

| Rule ID | Severity | Trigger | Suggested corrective action |
| --- | --- | --- | --- |
| TB-000 | BLOCKING | No active ledger balances exist | Import and activate a non-empty balanced Trial Balance |
| TB-001 | BLOCKING | Current signed Trial Balance total is not zero | Correct source/import sign or column mapping; do not create a suspense plug |
| TB-002 | BLOCKING | Comparative signed Trial Balance total is not zero | Correct comparative balances or comparative column/sign mapping |
| TB-003 | ERROR | A normalised ledger code occurs more than once | Give every imported ledger a unique stable source code and re-import |
| MAP-001 | BLOCKING | A material ledger is unmapped | Map to one active leaf taxonomy head and review it |
| MAP-002 | ERROR | A mapping points to an unavailable taxonomy node | Select an active Division I taxonomy head |
| MAP-003 | WARNING | A material balance is opposite to the mapped head's normal balance | Verify the sign, mapping and separate-presentation need |
| MAP-004 | BLOCKING | One ledger has more than one statement mapping | Retain exactly one reviewed mapping so the amount cannot be duplicated |
| MAP-005 | WARNING | A non-zero below-materiality ledger is unmapped and excluded | Map or explicitly clear the ledger so completeness is documented |
| ADJ-001 | BLOCKING | Journal debits and credits differ | Correct the journal lines before submission or posting |
| ADJ-002 | BLOCKING | Journal has fewer than two lines, a negative amount, both sides on one line, or a zero-value line | Correct the journal structure |
| ADJ-003 | WARNING | Submitted adjustment is awaiting review and does not yet affect statements | Approve/post or reject explicitly |
| ADJ-004 | ERROR | Journal line references a ledger absent from the active TB | Select an active ledger or recreate the journal after re-import |
| BS-001 | BLOCKING | Current assets differ from current equity and liabilities | Trace mappings, signs, posted adjustments and profit bridge |
| BS-002 | BLOCKING | Comparative assets differ from comparative equity and liabilities | Trace comparative mappings, signs and profit bridge |
| CF-001 | BLOCKING | Calculated cash movement differs from movement in mapped cash | Review cash-flow classification and explicit cash-flow inputs |
| REV-000 | INFO | All core automated reconciliations pass and no other automatic finding exists | Complete disclosure workpapers and professional review |

The synthetic seed also contains example persisted observations (`DISC-003` and `RATIO-001`) so the review workflow can be demonstrated. They are not silently treated as executed rules for a newly imported company.

## 11. Finalisation gate

Finalisation succeeds only when:

1. Active TB import is immutable, balanced, and hashed.
2. Required ledgers are mapped and mapping version is locked.
3. All intended adjustments are approved and posted; no unbalanced/draft material entries remain.
4. Balance Sheet, P&L bridge, notes, and cash flow reconcile in paise.
5. Latest validation run matches the current dataset hash.
6. No blocking results or unapproved errors remain.
7. Required warning resolutions and ratio explanations are complete.
8. Preparer and reviewer approvals exist for current versions.
9. A current verified backup has been generated.
10. Final snapshot and audit hashes are calculated successfully.

The resulting status reads **Financial Statements Ready for Review** before reviewer approval and **Finalised** only after approval and snapshot creation.
